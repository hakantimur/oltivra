# Load test — 2026-09-27 (stage infrastructure)

Spec §40.7. Locust (`backend/load/locustfile.py`) ran from a single workstation against a temporary Cloud Run
service `oltivra-load`. It used the stage image with fake auth, its own Firestore database `oltivra-load`, the
16 stage RTDB shards and the stage Cloud Tasks queues. The service was deleted after the run.

## Setup

- Cloud Run: 1 vCPU, 1 GiB, concurrency 20, max 20 instances, CPU always allocated, europe-west1.
- Workload: 300 concurrent players, spawn rate 5/s, 7 minutes. The mix was Quick, Survival, answer bursts at the
  scoring boundary, and sync fallback (no RTDB listener). Players had mixed latency bands, and bots filled rooms.
- Harness polling: every player polls `GET /v1/matches/{id}` about once per second. This is 68% of all requests.
  Real clients use RTDB listeners, so production traffic per player is much lower.

## Results (run 2, after the fixes below)

| Metric | Value |
|---|---|
| Requests | 103,302 (246 req/s) |
| Failures | 23 (0.02%). No 5xx. 22 were answers correctly rejected after the player was eliminated, 1 was a random invalid username |
| Median / p95 / p99 (API) | 140 / 310 / 940 ms |
| `matches/answer` p95 / p99 | 310 / 620 ms |
| Matches finished | 454 Quick, 202 Survival, all settled |
| Peak instances / CPU | 19 instances, CPU at most about 70% |

## Findings and fixes

1. **Firestore transaction contention (fixed).** Run 1 returned about 90 HTTP 500s with
   `409 Aborted due to cross-transaction contention`. They came from the matchmaking and settlement transactions.
   `google.cloud.firestore.transactional` only retries commit conflicts, not contention raised while reading, so
   `FirestoreDocStore.run_transaction` now retries `Aborted` up to 6 times with jittered exponential backoff.
2. **Harness join storm (fixed in the harness).** After a non-200 join the harness rejoined every 1–4 s. The queue
   rate limit returned 429s, the risk engine recorded `QUEUE_MANIPULATION`, and players got a temporary queue
   restriction (284 `QUEUE_RESTRICTED`). This is correct server behaviour. The harness now backs off like the app,
   honouring `Retry-After` and waiting at least 15 s.
3. **Instance limit.** Run 1 hit max instances (10) and got "no available instance" 500s from the frontend.
   Stage `oltivra-api` runs with max 3 instances. Before launch, size production as concurrency 40–80 with 2 vCPU,
   a minimum of 1–2 warm instances, and a max instance cap from a distributed run.

## Not covered yet

- 1,000 / 5,000 / 10,000 concurrent players. One workstation drives about 300 players with this harness. Larger
  stages need distributed Locust workers, for example a Cloud Run job or a small GKE pool.
- Cloud Tasks delay and duplicate injection (the `ChaosOperator` uses the shared-secret internal auth, and the
  service ran with OIDC). RTDB shard loss is also not covered.
